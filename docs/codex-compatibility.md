# Codex compatibility

Marr Work is a client of the local Codex app-server. It reuses the runtime's login, configuration, skills, and available integrations, and keeps its own interface and attachment storage. Compatibility is discovered from the running server rather than inferred from the installed desktop app's name.

The original Work integration was checked against schemas generated by Codex CLI **0.146.0**. The settings audit on **2026-10-18** uses locally generated schemas from **0.162.0-alpha.17.2**, alongside the [Codex app-server reference](https://learn.chatgpt.com/docs/app-server). The alpha schema also contains experimental and internal interfaces; their presence does not establish stable availability or imply that Marr implements them. Older or restricted runtimes can expose fewer methods. Capability errors remain visible without ending an active task.

## Runtime ownership (2026-10-28)

Marr runs without App Sandbox and launches the selected Codex executable directly with Foundation `Process`. Code signing and Hardened Runtime remain enabled. There is no embedded `MarrCodexServer.app` target, LaunchServices helper, helper lease timer, or helper image-transfer HTTP server.

Each instance launches `codex app-server --listen ws://127.0.0.1:<available-port>`, supplies the executable directories and standard package-manager paths in `PATH`, inherits `CODEX_HOME`, checks readiness, and tries later candidates on startup failure. Work, screenshot conversations and translation retain independent WebSocket connections to the same instance-owned server. Explicitly configured external servers remain connection-only. Turning sync off, changing the selected runtime/server or quitting stops only Marr's own child. Disconnecting a Work socket does not terminate the shared server while other clients may use it.

Sidebar preferences are read directly from allowlisted fields in `.codex-global-state.json` on a utility task, at most every two seconds while the sidebar is visible and the app is active. There is no intermediate snapshot file or heartbeat write. Manual server connections do not import this local desktop state. Historical image recovery reads thread-scoped archives on a coalesced, cancellable utility task into Marr's cache; it no longer launches a helper or transfers images over HTTP. Size limits and session identity checks remain enforced.

Existing sandbox data stays in place; fresh installs use normal Application Support. See [storage compatibility](local-workspaces-and-storage.md). The implementation and validation notes below include historical behavior from earlier builds; references to a helper describe that earlier architecture.

Enabling skills or managing plugins changes the selected runtime's shared configuration. Such changes may also affect other clients using that runtime. Task history and files are not copied to a separate cloud account by Marr.

## Settings interface audit — 2026-10-18

Settings now has separate **Account**, **Configuration**, and **Archived chats** pages. **Usage** distinguishes account-wide limits and activity from Marr's locally recorded token activity. The category rail scrolls in small windows, and the new pages are searchable in English and Chinese. Conversation and translation reasoning use discrete sliders built from the selected model's supported efforts; translation retains an explicit Automatic choice. Fork is available in the chat header menu; the Work composer keeps its placeholder to “Ask Codex” or “Add an instruction”.

| Settings surface | Implemented runtime contract |
| --- | --- |
| Account | `account/read` displays the current sign-in method, email, plan, and authentication requirement when provided. `account/login/start` supports ChatGPT browser login and device-code login; `account/login/cancel` cancels that login and `account/logout` signs out after the UI confirmation. `account/login/completed` and `account/updated` refresh the displayed state. Existing API-key sign-ins can be identified; entering an API key here is not implemented. |
| Account limits and activity | `account/rateLimits/read` prefers `rateLimitsByLimitId` and falls back to the legacy single bucket. It displays each available window's remaining percentage, reset time, and reported credit state. `account/rateLimits/updated` updates the relevant bucket. `account/usage/read` adds lifetime tokens, peak daily usage, current/longest streaks, and longest turn when returned. Missing values remain unavailable, rather than being interpreted as zero usage or a full allowance. |
| Configuration inspection | `config/read` with `includeLayers` and the selected working directory displays effective preferences, their origins, configuration layers, provider, sandbox, and approval policy. `configRequirements/read` supplies managed constraints. Arbitrary configuration values and credentials are not dumped into the UI. |
| Configuration changes | `config/value/write` is restricted to four keys: `web_search`, `model_verbosity`, `model_reasoning_summary`, and `analytics.enabled`. Writes target the discovered user configuration file with its `expectedVersion` and `mergeStrategy: replace`; Default sends a null value. Allowed web-search modes are filtered by managed requirements. Read/version failures and active work disable editing; the UI refreshes configuration after a write. Sandbox and approval policies remain read-only. |
| Runtime features | Paginated `experimentalFeature/list` displays the runtime's feature names, descriptions, stages, and enabled state. This page is read-only; it does not turn on experimental capabilities. |
| Archived chats | A dedicated page searches archived runtime chats and restores them through `thread/unarchive`. It uses runtime history rather than a separate copy of archived conversations. |

The audit cross-checked `ClientRequest`, `ServerNotification`, and the corresponding generated `v2` request/response definitions. In particular, `permissions` on thread creation is a named profile identifier, `expectedVersion` is a config-write concurrency check, and rate-limit reset credits require an explicit idempotent mutation. Those are separate contracts, not generic preference switches.

The following settings-related schema capabilities still lack a complete Marr interface:

| Remaining capability | Boundary |
| --- | --- |
| Permission profiles | `permissionProfile/list` discovery and selecting a named `permissions` profile for a thread are not implemented. Showing the effective sandbox/approval policy does not provide profile switching. |
| External-agent migration | `externalAgentConfig/detect`, `externalAgentConfig/import`, import history, and progress/completion notifications are not wired to an import workflow. |
| Realtime voice | `thread/realtime/listVoices`, session start/stop, audio/text/speech submission, and realtime transcript/audio notifications do not yet have a voice UI or audio pipeline. |
| Credit/reset actions | `account/rateLimitResetCredit/consume` is not invoked. Displaying credits does not redeem a reset, buy credits, or send `account/sendAddCreditsNudgeEmail`. Workspace account messages and upsell flows are not implemented. |
| Additional authentication | API-key entry, `account/gatewayOAuth/*`, and experimental `account/bedrock/*` setup are not exposed. Schema variants explicitly marked internal are not treated as supported client authentication flows. |
| Feature mutation | `experimentalFeature/enablement/set` is not exposed; feature discovery only reports state. |
| Broader configuration editing | `config/batchWrite`, arbitrary keys, instruction/profile editing, and custom permission-policy editing are not exposed. The four-key editor is intentionally smaller than the configuration schema. |

## Host boundaries

- A standalone app-server does not provide the Codex desktop host's injected tools, such as managing desktop tabs or windows, its automation scheduler, or host-specific artifact/session tools. An unsupported dynamic tool gets an explicit unsuccessful protocol response.
- The current schema does expose `thread/attachment/*` and thread-section operations. Its open-ended attachment payload does not by itself establish the desktop PR-card contract, and section identifiers do not document a reserved pinned section. Marr does not yet offer PR association, shared chat links, temporary side chats, scheduling, or independent chat windows from the reference menu; these need verified contracts and complete local lifecycles.
- Cloud Work tasks, Pages, native cloud artifacts, and account-specific connectors require their corresponding service or host APIs. Runtime-discovered app access is displayed; it is not a claim that every desktop or cloud workflow exists in Marr.
- The desktop settings screenshot is a navigation reference, not an app-server API inventory. Parental controls, trusted contacts, pets, passwords, computer history, Appshots, browser management, and cloud computers belong to their respective desktop/cloud services. Marr does not add nonfunctional settings entries for them. Any future support needs an actual service integration and its own lifecycle; it cannot be inferred from `config/read` or app/plugin discovery.
- Interactive MCP application HTML and custom resource schemes are retained as output but are not executed inside Marr. Supported images and ordinary links can be opened or previewed explicitly.
- Unknown protocol items remain inspectable. Unknown request methods receive a JSON-RPC method-not-found error instead of a fabricated approval or success.
- Installation policies and unsupported form schemas are respected. A feature absent from a selected runtime remains visibly unavailable.
- CLI command discovery does not imply complete CLI parity. Unsupported commands preserve the draft and are never silently sent as ordinary prompts. Dynamic service-tier commands, presets, shell mode, and desktop-only attachment surfaces (such as attaching a foreground application, recording a skill, or drawing) remain outside this implementation. The popup lists supported commands; `/help` retains the full compatibility audit. Native plugin artwork and rich inline mention chips are not implemented.

These boundaries mean Marr is not yet a replacement for every Codex desktop or ChatGPT Work host feature. The implemented scope is the public local runtime contract and its native Work interface.

## Workspace sidebar and shared history refresh (2026-10-23)

The answer window now has one expandable Chats sidebar in Conversation and Work.
Codex conversations are nested below their workspace directories, with collapse,
show-more, title/path search and selected-task status. Local screenshot conversations
have their own group. The subsequent visual refinement follows the supplied Apple
Notes recording: an inset rounded sidebar surface, compact folder/count rows, and
secondary tools revealed on hover or keyboard focus. Shared upper-left window
controls remain outside the sidebar's clipping region throughout the transition.

On the first expansion, the window widens when screen space permits. Collapsing
the sidebar keeps the expanded window width and returns that space to the
conversation. Later expansions reuse the existing width rather than adding another
sidebar width. Manual window moves and resizes are retained, subject to minimum
size and visible-screen bounds. The first native-window expansion uses a 240 ms
system animation with `cubic-bezier(0.165, 0.84, 0.44, 1)` easing. While its width
changes, sidebar reveal and toolbar position derive from the actual viewport;
they do not run an independent SwiftUI timeline. At a retained window width,
the sidebar uses a SwiftUI translation animation with the same timing.
Conversation content uses the target
width throughout the transition and stays centered in the current viewport,
avoiding an initial position jump. Reduced Motion and unpresented windows apply
the final layout immediately. A screen edge may constrain the available
conversation width.

Foreground history refresh is read-only: `project/list`, `thread/list`, and
`thread/read` with `includeTurns: true`. The selected conversation is polled roughly
every 3 seconds and the catalog roughly every 12 seconds, subject to request time,
other foreground work and exponential error backoff (up to 60 seconds). Minimizing,
closing, switching to settings, or leaving the application stops scheduled polling.
Nothing in polling calls `thread/resume`, `turn/start`, or approval methods.

The thread list explicitly requests `cli`, `vscode`, `appServer`, `exec`, and
`unknown` sources with no cwd/provider filter. Unsupported experimental
`project/list` falls back to directories discovered from thread `cwd`. The current
workbench uses non-null canonical `projectId` when the runtime supplies it,
retaining `cwd` separately for execution. Legacy desktop conversations can have a
null `projectId` even when assigned to a project. For those records, Marr reads
allowlisted desktop project assignments, then falls back to workspace root hints
or the execution directory. The longest matching project root wins, with path
component boundaries enforced. Explicit desktop projectless records and
acknowledged local removal from a project stay under Conversations. Membership
resolution is cached and invalidated when tasks, projects or desktop state change.

Cross-client visibility depends on using the same runtime history / `CODEX_HOME`.
Separate app-server processes do not provide a shared live token subscription.
`thread/read` obtains stored history without loading or subscribing to the thread;
`notLoaded` or a synthesized interrupted turn is not proof that another client
stopped working. Refresh preserves uncertainty until it obtains a reliable outcome
for the observed turn. Changed snapshots merge into the selected transcript without
replacing its unsent composer draft. Selection/runtime epochs reject late replies.
The last acknowledged turn ID is saved before its first delta so a restarted Marr
can verify that exact turn's completion instead of guessing from an earlier turn.

Older legitimate interrupted turns can lack `completedAt`; they cannot be
reliably distinguished from an in-progress turn projected by another server. In
that state, the user can explicitly choose **Resume in Marr…**, confirm that the
other client has stopped, and load the saved conversation. This action sends only
`thread/resume`; it neither sends a new message nor repeats an earlier command.
Background refresh never takes this path. See the [official older history test](https://github.com/openai/codex/blob/rust-v0.146.0/codex-rs/app-server-protocol/src/protocol/thread_history.rs#L2416-L2438).

Protocol references: [official app-server documentation](https://learn.chatgpt.com/docs/app-server)
and the [Codex app-server source](https://github.com/openai/codex/tree/e6ebdfe00b520e21ed50ac0362656f32dd64d2fc/codex-rs/app-server/src).
Validation uses temporary workspaces and injected protocol fixtures; it does not
read real VS Code conversations or submit a model request.

## Shared sidebar state (2026-10-23)

The local desktop CLI 0.163.0-alpha.11.2 experimental schema and read-only live
`project/list` / `threadSection/list` queries were checked. The Homebrew CLI
0.146.0 does not expose the same project/section capabilities. Marr prefers the
bundled desktop runtime. The public [app-server documentation](https://learn.chatgpt.com/docs/app-server)
provides the general protocol; these sidebar extensions remain experimental.

- Thread pin/unpin uses `thread/section/move`, with the desktop's built-in Pinned
  section ID. Only acknowledged mutations update the local view; failed requests
  leave the prior state and show the capability error. Polling imports external
  section changes and retrieves pinned order using `section_position`.
- Project assignment uses `thread/metadata/update` (empty project ID clears it).
  New conversations send the selected canonical project ID with `thread/start`.
  Membership changes do not change the execution directory or start a turn.
- Project pins and sidebar grouping/sort preferences are private desktop state.
  Marr directly reads only allowlisted fields from `.codex-global-state.json`
  on a utility task while its sidebar is visible and active. The parsed state
  includes thread-to-project assignments, projectless thread IDs and workspace
  root hints. Marr never writes the source file or exports drafts, credentials
  or unrelated preferences. Unchanged state does not rebuild the sidebar.
  Manual server connections do not consume local desktop state.

- Those desktop-owned preferences are followed in one direction. Project pin
  and local reorder actions are disabled while following them; unsupported
  runtimes report errors instead of claiming a successful shared mutation.
  The current UI presents project pins and conversation pins separately, so
  mixed project/chat pin ordering and custom sections are not mirrored yet.
- Group expansion remains local and collapsed by default, as requested. Model,
  approval and other execution preferences are not changed by this bridge.

This is eventual synchronization of stored state, not a shared live token
subscription: foreground catalog polling is normally twelve seconds, selected
history polling three seconds, and desktop preference reads two seconds. Tests
use isolated defaults and mock RPC responses, never mutate the user's Codex
preferences, and never start real model turns.

## History selection deadlock (2026-10-24)

A 20-second read-only sample of the user's running Debug app captured the same
lock inversion throughout: the sidebar selection called `activateWorkspace`,
then `selectWorkspace`, then synchronous archive `save`. The main thread waited
for the serial persistence queue. That queue was inside `UserDefaults.set`,

conversations. Selected stack frames are retained in
`build/validation/history-deadlock-stacks.txt`.

Archive encoding remains on the serial background queue. It prepares only data

and shutdown flushes wait only for encoding, then commit preferences on the main

prepared data, so old callbacks cannot overwrite a terminal snapshot. The v1
archive format and existing conversation data are retained.
